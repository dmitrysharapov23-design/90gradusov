# План цифрового производства «90 градусов»
Предложение к обсуждению, 13.10.2026. Сроки и бюджет не оценены. Портал, тариф, права, калькуляция и чертежи не обследованы.

Система: Битрикс + производственный модуль + QR/Telegram для рабочих.

## Что должна дать система
- Рабочему: понятное текущее задание и простая фиксация результата.
- Начальнику: очередь, загрузка людей и станков, причины задержек.
- Менеджеру: готовность заказа и ожидаемый срок.
- Владельцу: подтверждённые трудозатраты и сравнение плана с фактом.

## Цель
Видеть задания и загрузку цеха, учитывать труд по каждой позиции заказа, сравнивать расчётные и фактические затраты, затем использовать достоверные данные для планирования и мотивации.

## 1. Устройство
- Битрикс: заказчик, договорённости, документы, срок, оплаты, общий статус.
- Google-таблица: калькулятор; утверждённый расчёт сохраняется отдельной версией и связывается с позициями.
- Производственный модуль: партии, маршруты, задания, рабочие сеансы, результаты, материалы, причины задержек.
- Telegram-бот по QR для рабочих; доска заданий и загрузки в браузере для начальника.
- Хранилище: база сервиса (например PostgreSQL). Сообщения Telegram не журнал учёта. Для пилота достаточно одного небольшого приложения и базы.

Источники данных:
| Данные | Источник |
|---|---|
| Клиент, условия, состав заказа, срок | Битрикс и утверждённая спецификация (выбрать единственную редактируемую запись) |
| Исходная оценка и план часов | Зафиксированная версия калькуляции |
| Допуск в производство | Подтверждённые оплата, чертёж, материалы, маршрут |
| Время, выпуск, брак, остаток работы | Производственный модуль |
| Реальная оплата | Банк/бухгалтерия либо подтверждение уполномоченного с документом |
| Получение и расход материала | Приёмка и списание/возврат, привязанные к заказу |

ИИ: разработка, черновики КП, объяснение отклонений. Формулы, таймеры, права и переходы статусов выполняет обычный проверяемый код.

## 2. Сквозной процесс и условия переходов
| Шаг | Что фиксировать | Когда дальше |
|---|---|---|
| Лид → расчёт | ТЗ, позиции, количество, материал, обработка, срок, ответственный | Данных достаточно; неизвестное отмечено явно |
| Расчёт → КП | Материалы, план операций и часов, внешние работы, расходы, цена, версия | Менеджер/начальник подтвердили цифры; текст КП соответствует |
| КП → договор → 70% | Состав, версия цены, условия, подтверждение денег | Условия запуска подтверждены; изменение состава оформлено отдельно |
| Проектирование | Задания проектировщику (в штате 1 + внештатный чертёжник; на 13.10 было двое), очередь, срок, версия чертежа, автор, время согласования | Версия согласована и разрешена к изготовлению |
| Подготовка | Партии, маршрут, материал принят, станок/оснастка доступны | Начальник разрешил выпуск заданий |
| Производство | Задания, люди, оборудование, время, принятые количества, проблемы | Результат операции принят; следующей операции доступно нужное количество |
| Контроль → упаковка | Качество, комплектность, упаковочные места, фото при необходимости | Все позиции готовы либо утверждена частичная отгрузка |
| Остаток 30% → отгрузка | Подтверждение оплаты, отгруженные позиции/количества, дата, документы | Исполнено условие оплаты, подтверждена физическая передача |
| Закрытие → следующий расчёт | План/факт, причины потерь, фактические затраты, выводы по нормам | Начальник/владелец проверили; новые нормы только на будущие расчёты |

Физическую готовность, оплату, передачу и хранение учитывать отдельными признаками. «Ответственное хранение» не автоматический шаг после каждой отгрузки: определить, кто владеет товаром, кто хранит, когда была физическая передача. Возможны частичные отгрузки.
Воронку «Производство» сохранить для общего обзора, детали людей и операций не превращать в десятки стадий. На пилоте общий статус подтверждает начальник; автопереходы добавлять после согласования правил и проверки действующих роботов.

## 3. Минимальная модель учёта
Заказ → позиция → партия → операция → сеансы работников + результат операции.

- Заказ: внутренний ID, ID в Б24, срок и приоритет, менеджер, ссылка на калькуляцию.
- Позиция: устойчивый ID, наименование, количество, единица, материал, спецификация.
- Партия: ID позиции, разрешённое количество, версия чертежа, маршрут, QR, происхождение при разделении.
- Операция: тип/подтип, зависимости, станок/квалификация, план наладки и обработки, единица выпуска, количество деталей на изделие, доступный и оставшийся объём.
- Рабочий сеанс: работник, операция, начало/конец, вид времени, причина остановки, источник и статус проверки.
- Результат: принято годных, на доработку, брак, кто и когда подтвердил; количество регистрируется один раз.
- Проблема: категория, объект, кто обнаружил, время открытия/решения, ответственный, блокирует ли работу.
- Ставка: вид затрат, величина, период действия, состав, право просмотра.
- Материал: получено, использовано, возвращено/остаток, отходы, стоимость и распределение по позициям.

Маршрут задаётся под изделие: резка листа/трубы → гибка → предсварочные → сварка → полировка/шлифовка → покраска/очистка → сборка → упаковка. Ненужные операции исключаются; для параллельных деталей задаются зависимости, для сборки готовность комплектующих. Подрядная покраска отдельное задание (отправка, срок возврата, стоимость).
Единица выпуска операции может отличаться от изделия (16 ножек ≠ 16 столов). Нужны состав изделия и коэффициент комплектации; перед сборкой проверка наличия всех деталей. Для первой версии допустим учёт «комплект деталей на изделие». Стоимость детали не делить на число столов без связи состава; выпуск деталей не суммировать с выпуском изделий.
«Простой» это вид времени, а не операция. «Прочее» требует комментария и еженедельного разбора. Обслуживание оборудования и приёмка сырья самостоятельные задания; на заказ относить только при обоснованной связи, общие затраты распределять отдельно.

## 4. Рабочий сценарий QR и кнопок
1. Начальник выпускает партию и печатает QR на маршрутном листе (номер заказа, позиция, количество, версия чертежа).
2. Работник сканирует QR камерой; бот показывает изделие, количество, действующую версию; работник подтверждает операцию и жмёт «Начать».
3. При проблеме: «Есть проблема» + причина; затем выбор: продолжаю / остановился / перешёл на другое задание.
4. При остановке: «Прервать» или «Завершить». Для завершения: количество и результат; приёмка по роли.
5. Начальник видит неполный выпуск, проблемы, забытые таймеры; в конце смены подтверждает исключения.

Стартовые причины: сложность работы, нет инструмента/станка, ошибка производства, ошибка модели/чертежа, нехватка материала, нехватка людей, смена задания. Если проблемы нет, причина не нужна. Отметка проблемы и фактический простой учитываются отдельно.
QR содержит короткий непрозрачный идентификатор партии, без персональных данных, стоимости и секретов. Сканирование не заменяет проверку учётной записи. Сервер показывает актуальные количество и ревизию; при замене чертежа старая бумага обнаруживается и требует проверки; старые сеансы сохраняют исходную ревизию.
Крупные кнопки, мало действий. Резервный ввод мастером (реальное время + пометка происхождения) при разряженном телефоне/плохой связи. Telegram-бот не даёт офлайн-учёта. Общий терминал только с однозначным подтверждением работника.

## 5. Правила, без которых цифры неверны
- Один человек не ведёт два таймера ручного труда одновременно; переключение закрывает/приостанавливает предыдущий сеанс явным действием.
- Два работника по часу = 2 человеко-часа. Час станка и календарный час отдельные величины (цикл лазера идёт, пока оператор занят другим).
- Бригадный выпуск регистрируется один раз, труд для каждого участника. Переделка не создаёт дополнительный годный выпуск.
- Наладка относится на партию, обработка на выполненный объём.
- «Стоп» ≠ «всё готово»: частичное завершение, годные, брак, остаток; при разделении партии сохраняется происхождение.
- Пометка «сложно» объясняет событие, не увеличивает норму автоматически и не доказывает вину. Изменение нормы утверждается отдельно.
- Ожидание партией материала не значит простой работника.
- Повторный клик, повтор webhook, восстановление после сбоя не создают второй сеанс/выпуск (уникальные ID, транзакции, проверка последовательности).
- Таймер хранится на сервере; слишком длинные/незакрытые сеансы попадают в исключения, а не в достоверный труд за ночь.
- Исправления сохраняют исходную запись, автора, причину, время; поздние события не переписывают подтверждённые итоги незаметно.

## 6. Планирование цеха
Первый уровень: ручной план на смену с проверкой доступности, без оптимизатора. Рабочий видит текущее и следующее задание. Начальник видит очередь по участкам: не готово к запуску / доступно / назначено / в работе / заблокировано / на приёмке / готово. В карточке: заказ/позиция, количество, остаток, срок, приоритет, работник, ресурс.
Задание доступно, когда согласован чертёж, есть материал/оснастка, доступны результаты предыдущих операций. Ограничения оцениваются отдельно по лазеру, гибке, сварке, сборке, квалификациям. Начальные оценки времени даёт начальник производства (помечаются как экспертные, пересматриваются по статистике). Дата готовности зависит от очереди, смен и узкого места, а не от суммы трудочасов.

## 7. Себестоимость и замыкание на калькуляцию
- Формула «материал + коэффициент сложности» может остаться способом формирования цены на первом этапе, но плана часов в ней нет. Нельзя задним числом объявлять часть коэффициента планом труда без отдельного правила и утверждения.
- В расчёт добавляются план наладки/обработки по операциям, внешние работы, состав производственных расходов. Сохраняются исходная оценка, согласованная версия заказа, изменения по просьбе заказчика. Перерасход сравнивается с сопоставимым утверждённым объёмом; рост цены из-за нового объёма показывается отдельно.
- Прямой труд = сумма по работникам (подтверждённые часы × ставка периода). Пример: 2 работника, 4 годных изделия за час, ставки 600 и 800 ₽/ч → 2 чел-часа, 1 400 ₽ на партию, 350 ₽/изделие.
- Производственная себестоимость: фактический материал + прямой труд + внешние работы + обоснованная доля прочих расходов. Не дублировать затраты (машинная ставка и оператор/энергия/амортизация; общие расходы и уже распределённый ФОТ).
- При окладе часовая ставка это управленческое распределение. Определить, что в ней учтено и по какой базе; ежемесячно сверять прямой + косвенный труд + отклонения с фактическим ФОТ на одной базе (не смешивать «на руки», начисления, полные расходы работодателя).
- Материал: мини-реестр потребность → заказано → принято → выдано на позицию → использовано/возвращено/отходы.
- Незавершённая партия показывает накопленные затраты и остаток работы, а не окончательную стоимость единицы. В закрытой однородной партии затраты по правилу распределяются на фактический годный выпуск; брак и переделки видны отдельно. При частичной отгрузке распределять затраты между выпущенным и незавершённым.
- Пока измерены только часы и ставки, отчёт называется «Трудозатраты и стоимость прямого труда». «Полная фактическая себестоимость» только после подключения материалов и согласованных расходов.

## 8. Показатели и премирование
Первая панель:
- По заказу/позиции: срок, где работа, готово/осталось, план/факт часов и затрат, причины отклонений.
- По цеху: очередь и загрузка ресурсов, блокировки с ответственными, просрочки, ожидаемый выпуск.
- По качеству учёта: незакрытые сеансы, пропущенные результаты, исправления, незаполненные причины.
- По выпуску: принятые операции/изделия, переделки и брак, прямое/косвенное время.
Несопоставимые изделия не объединять в «выработку в штуках».
Премирование: сначала несколько недель устойчивых данных; на пилоте оплата не меняется; затем месяц параллельный расчёт возможной премии с показом сотрудникам и разбором споров. Рассматривать принятый качественный выпуск в обоснованных нормо-часах, результат команды, контролируемые сроки. Не платить за факт включённого таймера; не судить человека по неконтролируемым причинам (ожидание материала, ошибка чертежа). Нормы и вклад бригады согласовать до денежного применения; схема оплаты не утверждена.

## 9. Что нужно для разработки и эксплуатации
- Ноутбук и инструмент разработки (не постоянный сервер).
- Приватный Git-репозиторий (GitHub), владелец бизнес.
- Облачное размещение приложения и базы (после проверки доступности из цеха и требований к данным).
- Telegram-бот и служебная настройка Б24; учётные записи принадлежат бизнесу, доступы минимальные.
- Тестовый стенд.
- Хранилище документов и резервных копий (чертежи по версиям, копии базы и конфигурации, отдельные права).
- Технический ответственный (обновления, сбои, доступы, восстановление); менеджер ведёт справочники по инструкции.
Claude Code доступен в Pro/Max с общими лимитами плана; подписка не заменяет размещение, базу, резервирование, поддержку. Для обычного учёта времени API нейросети не нужен.

Чек-лист для подрядчика Б24:
1. Тариф, регион портала, подписка/доступность REST, права интеграционного пользователя.
2. Где заказ и его позиции, какие ID устойчивы, как хранятся версии файлов и утверждение чертежа.
3. Какие роботы/бизнес-процессы реагируют на стадии (чтобы обратная синхронизация не запустила лишнее).
4. Как читать новые/изменённые заказы, восстанавливаться после пропуска события, какие итоговые поля можно писать.
5. Тестовая запись/стенд и матрица прав (рабочий, мастер, менеджер, владелец). Рабочему не нужны контакты клиентов, чужие ставки, прибыль.
Ключи и токены только через настройки сервиса/хранилище секретов, не в чатах и Git, не в QR.
Резервирование: база, файлы, настройки; копия отдельно от рабочего приложения; согласовать допустимую потерю данных и срок восстановления; пробное восстановление. Предложение для пилота: ежедневная копия плюс журнал базы, если потерять смену недопустимо. Git хранит код, а не рабочую базу.

## 10. Порядок внедрения и приёмка
1. Разобрать один настоящий заказ целиком (калькуляция, позиции, чертёж, путь до отгрузки; утвердить идентификаторы, маршрут, выпуск, права; зафиксировать неизвестные тариф/API и источник оплат).
2. Минимальный учёт: импорт одного заказа, выпуск QR, авторизация, старт/стоп, причина, количество, доска мастера, экспорт, исправления, резервирование. Без изменения зарплаты.
3. Пилот на 2–3 заказах с разными маршрутами и несколькими работниками разных участков; ежедневная сверка с мастером; затем расширение до восьми работников.
4. Планирование и план/факт: план по операциям и ресурсам, закупки/расход, версии сметы, контроль сроков; оценка качества данных за несколько недель.
5. Замкнуть цикл: статистика в калькуляции, проектирование, отгрузка/хранение, согласованные автодействия Б24; премии сначала параллельно.
Если пилот охватывает не все операции, отчёт показывает неполный охват; отсутствие записи не означает нулевые затраты.

Приёмочные сценарии:
- Обычная партия от начала до принятого результата и отчёта по позиции.
- Два человека на операции: труд суммируется, выпуск не удваивается.
- Смена задания, забытый стоп, отключение сети, повтор кнопки и webhook.
- Частичный выпуск, брак/переделка, разделение партии с сохранением происхождения.
- Разные единицы выпуска: детали не считаются изделиями; сборка при подтверждённой комплектности.
- Новая версия чертежа: старая бумага выявляется, прежний факт сохраняется.
- Отказ Б24: цех продолжает локальный учёт, очередь синхронизации восстанавливается без дублей, видна свежесть связи.
- Недоступность сервиса: резервный ввод без выдуманного времени и незаметного переписывания итогов.
- Рабочий не видит чужие ставки; отключённому сотруднику закрыт доступ.
- План/факт воспроизводится из исходных записей; копия базы восстанавливается на тестовом стенде.
Главный результат первой версии: начальник показывает, кто делает какую позицию, что принято, что мешает следующей операции, сколько подтверждённых человеко-часов потрачено.

## Приложение: ориентиры для разработчика
(Документация проверена 13.10.2026; применимость и права подтвердить на конкретном портале.)
- Сделки: crm.item.get; товарные строки: crm.item.productrow.list. Связывать позицию по ID и версии состава (название, номер строки и каталожный ID по отдельности недостаточны); при пересоздании строки явное сопоставление.
- Для одного портала возможны вебхуки; для встроенного интерфейса может понадобиться локальное приложение.
- События изменения заказа дополнять сверкой пропусков; учитывать лимиты облачного REST. Время сначала пишется в базу сервиса, запись сводки в Б24 через очередь.
- ID файлов CRM и ID объектов Диска различаются; ссылка на файл ≠ утверждённая ревизия.
- Telegram deep link: параметр start до 64 base64url-символов, подходит для непрозрачного ID партии.
- Bot API: update_id для устранения дублей, плюс защита самого действия в базе. Неполученные updates хранятся ≤24 часа, это не резервная копия.
